# CaloLog 产品蓝图 PRD v1

> 版本：v0.1（蓝图草案）
> 更新日期：2026-08
> 定位：**日志型减脂健康应用**——尽可能简单，从"记录"开始，用创新方法降低记录门槛。

---

## 一、产品定位

**一句话**：一个让减脂人群"愿意每天坚持记录"的极简日志 App。

- 核心价值：把"记录"这件事做得足够简单，简单到用户不需要称、不需要换算、不需要研究营养学，就能完成一次记录。
- 目标用户：想减脂但被"精确记录热量"劝退的普通人（含开发者本人）。
- 商业愿景：从个人工具起步，验证价值后发展为独立商业应用，上架 App Store / Google Play。

**设计原则**：
1. **极简优先**：V1 只做"日志"，不做社区、不做智能推荐、不做拍照识别。
2. **日志是骨架**：所有功能都以"往日志里加一条记录"的形式存在。
3. **降低记录摩擦**：每一个功能设计都要回答"这能减少用户 10 秒还是 10 分钟？"。

## 二、V1 功能范围（三大模块）

### 模块 1：基础身体记录（体重/体脂/血糖）

| 功能 | 说明 | 优先级 |
|---|---|---|
| 体重记录 | 每日称重输入，支持连续曲线 | P0 |
| 体脂记录 | 可选字段，与体重并列 | P1 |
| 血糖记录 | 可选模块（糖尿病/控糖用户），需在设置中显式开启 | P1 |
| 指标趋势图 | 按日/周/月查看曲线，平滑波动 | P0 |

> 设计约束：血糖属于敏感健康数据，默认关闭、显式开启，且记录为"用户自行录入"，App 不做医疗建议。

### 模块 2：热量记录（核心模块）

**需求背景**：中国食品标签普遍用**千焦（kJ）**，而健身圈习惯用**大卡（kcal）**，用户每次看标签都要心算换算，是记录最大的摩擦点。

| 功能 | 说明 | 优先级 |
|---|---|---|
| 热量日志 | 按餐次（早/午/晚/加餐）记录每次摄入 | P0 |
| **千焦 ⇄ 大卡自动换算** | 用户输入千焦自动转大卡，反之亦然；**全 App 统一以"大卡"为主单位显示**，千焦仅作输入时换算 | P0 |
| 换算系数 | 1 kcal = 4.184 kJ（科学标准）；输入时提供"kJ 模式/ kcal 模式"切换，结果即时换算 | P0 |
| 食物快捷项 | 常用食物一键添加（用户自建收藏），减少重复输入 | P1 |
| 每日热量合计 | 当日累计 + 与目标对比 | P0 |

> **核心交互（换算）**：
> - 输入框旁有单位切换（kJ ⇄ kcal）；
> - 用户输入 1000kJ，App 实时显示 ≈ 239 kcal；
> - 历史记录统一以大卡存储，保证统计口径一致。

### 模块 3：创新估算方法（"一拳"体积估算）★ 差异化卖点

**需求背景**：用户在外面吃饭/吃食堂时没有秤，不知道"一个馒头多少克"。业界常用"手掌法则"（一拳≈1 杯 ≈ 240ml 等经验值），但**每个人的手大小不同，经验值误差大**。

**核心创意：按用户手的大小个性化估算食物体积 → 热量。**

#### 3.1 手掌测量

| 功能 | 说明 | 优先级 |
|---|---|---|
| 手动输入手长 | 用户用尺子量手掌长度（腕线 → 中指指尖）后输入 | P0 |
| **触摸屏测量（创新交互）** | 用户把手指/手掌放在手机屏幕上，通过**多点触控捕获两个触点之间的距离**，结合设备 PPI（每英寸像素数）换算实际长度 | **已决策：暂缓（未来开发）**——Web 端无法获取真实物理 PPI，精度不足；留待原生端（Capacitor）实现，详见文末决策记录 |

> 技术思路（触摸测量）：
> 1. 全屏进入测量模式，屏幕上显示两个引导点；
> 2. 用户张开拇指与小指（或食指与中指）按住两个点，捕获两个触点的屏幕像素距离 `d_px`；
> 3. 通过设备屏幕 PPI 换算真实距离：`d_cm = d_px / PPI * 2.54`；
> 4. 多次采样取中位数，减少手指按压面积造成的误差；
> 5. 由"指距"再关联"手掌长度"（可加入校准步骤：先测一个已知物体如硬币直径，标定真实 PPI——部分设备的 PPI 获取不可靠）。

#### 3.2 体积 → 热量估算

| 功能 | 说明 | 优先级 |
|---|---|---|
| "一拳"体积模型 | 由手掌尺寸推导"一拳"的体积（拳头近似椭球/圆柱体，V = f(手长)），建立**每用户个性化的一拳体积** | P0 |
| 自然语言快捷输入 | 用户输入"一拳馒头"，App 用馒头密度 × 一拳体积估算克数，再查食物热量密度表得大卡 | P0 |
| 常见食物密度/热量库 | 馒头、米饭、苹果等 V1 内置 20–50 个常见食材的「密度(g/ml) + 热量(kcal/100g)」 | P0 |
| 估算置信度提示 | 估算结果标注"±30% 误差"等提示，管理用户预期 | P1 |

> **估算公式（草案）**：
> - 拳头体积：以手长为输入的椭球近似（`V ≈ 4/3·π·a·b·c`，其中 a/b/c 由手长线性映射，需采集数据校准）；
> - 食物克数：`克数 = 体积 × 食物密度`；
> - 热量：`kcal = 克数 / 100 × 食物热量密度(kcal/100g)`；
> - 例：用户一拳体积 240ml，"一拳馒头" → 240ml × 0.5g/ml ≈ 120g → 馒头 223kcal/100g → **≈ 268 kcal**。
>
> **校准数据需求（后续）**：需要真实采集"手长 vs 拳围 vs 一拳体积"的关系数据（线下小样本即可起步，V1 用经验系数）。

## 三、非目标（V1 明确不做）

- ❌ 好友/社交系统（列为未来方向）
- ❌ AI 拍照识别食物
- ❌ 智能推荐/教练计划
- ❌ 运动记录（跑步/举铁等）
- ❌ 云同步/多端（初期本地存储，后续再加）

## 四、未来拓展路线（远期蓝图）

1. **好友系统**：互相可见打卡/日志，形成减脂陪伴（用户已提出）；
2. **云同步 + 账号体系**：多设备、数据备份；
3. **食物数据库扩充**：OCR 扫描食品标签、条形码查询；
4. **AI 估算升级**：拍照估份量，替代"一拳"模型；
5. **穿戴设备接入**：Apple Health / 体重秤数据自动同步；
6. **商业化**：订阅制（高级食物库/趋势分析）、或免费 + 广告。

> 路线原则：**每一步都从"日志"生长出来**，不为了做功能而做功能。

## 五、数据模型草案（V1）

```
User（本地）
├── id
├── hand_profile: { palm_length_cm, fist_volume_ml(推导), measure_method: manual|touch }
└── settings: { unit: kcal, glucose_enabled: bool }

BodyLog（身体记录）
├── date, type: weight|body_fat|glucose
├── value, unit
└── note?

FoodLog（热量记录）
├── date, meal: breakfast|lunch|dinner|snack
├── item_name, source: manual|fist_estimate|favorite
├── kcal（统一单位存储，kJ 输入时已换算）
├── kj_raw?（仅保留输入原始值）
├── estimate_confidence?（拳头估算时: ±%）
└── meta: { fist_volume_ml?, food_density?, grams? }

FoodLibrary（内置/收藏食物库）
├── name, density_g_per_ml?, kcal_per_100g
└── category
```

## 六、验证与迭代计划

| 里程碑 | 内容 | 验证目标 |
|---|---|---|
| M0 原型 | 热量换算 + 体重日志 + 一拳估算（本地版） | 开发者本人连续使用 2 周，记录摩擦是否真的低 |
| M1 内测 | 邀请 5–10 位减脂朋友使用 | 留存：7 日后再使用的比例；最常用功能排序 |
| M2 上架 | App Store + Google Play 发布 V1 | 首 100 用户反馈；"一拳估算"使用率是否 >30% |

**关键指标（V1 阶段只盯 3 个）**：
1. **次日留存**（日志类 App 的生命线）；
2. **人均每日记录条数**（≥2 条算健康）；
3. **"一拳"估算功能使用率**（差异化卖点是否被接受）。

## 七、技术决策记录（DECISIONS）

| 日期 | 决策 | 原因 |
|---|---|---|
| 2026-08 | **网页优先（Web-first）**，技术栈 React + TypeScript + Vite + Tailwind；部署 Cloudflare Pages；后期用 Capacitor 包壳上架 | 初期迭代快、零成本、更新即时；代码重合度 90%+，后期无缝转 App |
| 2026-08 | **触摸屏测量（手放屏幕测手长）暂缓**，留待原生端开发 | Web 端无法获取真实物理 PPI，测量精度不足；初期用手动输入手长（P0）不阻塞核心"一拳估算"逻辑 |
| 2026-08 | M0 阶段**纯本地存储**（localStorage），不做账号/云同步 | 符合极简原则；个人使用 + 朋友内测够用 |
